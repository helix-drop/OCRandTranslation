# 脚注尾注筛选器设计

## 样例结构结论

当前仓库里只有一组样例，但已经足够暴露出几个关键事实：

- 原始 PDF 是 [`脚注尾注的test.pdf`](../脚注尾注的test.pdf)。
- OCR markdown 是 [`脚注尾注的test.pdf_by_PaddleOCR-VL-1.5.md`](../脚注尾注的test.pdf_by_PaddleOCR-VL-1.5.md)。
- 版面 JSON 是 [`脚注尾注的test.pdf_by_PaddleOCR-VL-1.5.json`](../脚注尾注的test.pdf_by_PaddleOCR-VL-1.5.json)。

从 JSON 里可以直接看到 `model_settings.markdown_ignore_labels` 包含 `footnote`。这意味着：

- `md` 不是完整真相。
- 真正的页脚脚注，大多只存在于 `json.parsing_res_list` 里。
- 书末或章末的 `NOTES` 区，因为经常被识别成普通 `text`，反而会漏进 `md`。

样例里至少有三种不同的“注”：

1. 正常页脚脚注  
   例如第 1-3 页的 `1.` 到 `8.`。
2. 跨页的大脚注  
   例如第 29-30 页，正文里是 `libéralisme*`，后面整块星号脚注跨页延续，其中还夹带 `1. 2. 3. 4.` 这样的列表项，但它们不是尾注。
3. 显式尾注区  
   第 31 页出现 `### NOTES`，后面第 31-34 页是独立尾注区，编号为 `1-18`。

因此，筛选器不能只看一种信号：

- 不能只看 `md`
- 不能只看 `block_label == footnote`
- 不能只看“数字开头”
- 不能只看“页面下半部”

它必须是一个结合“版面 + 文本 + 上下文状态”的状态机。

## 设计目标

筛选器需要同时满足四件事：

1. 把正文、脚注、尾注拆成不同的数据层。
2. 把跨页脚注识别成一个注，而不是多段碎块。
3. 生成可稳定复用的注释 ID，避免数字冲突。
4. 让 Obsidian 中的成品既可读，又能在翻译后保持同构。

## 推荐数据来源优先级

### 1. JSON 是结构主源

主要依赖这些字段：

- `block_label`
- `block_content`
- `block_bbox`
- `block_order`

用途：

- 判断一页里哪些块是正文，哪些块是脚注区
- 判断脚注是否从页底开始，还是已经跨页蔓延
- 找到 `### NOTES` 之类的显式尾注标题

### 2. Markdown 是线性文本主源

主要用它做两件事：

- 抽取正文里的引用标记
- 作为后续分段翻译的正文底稿

但要明确：`md` 只能作为“正文和尾注的线性文本”，不能作为“完整注释定义源”。

### 3. PDF 只做回查和人工抽检

在筛选器里，PDF 不适合做一手结构判断，但适合做两类校验：

- OCR 出现可疑脚注标记时回查
- 大模型翻译后，人工核对版面是否还保持原有注释关系

## 判定逻辑

### 第一步：先切 section

先按明显的大标题切分逻辑 section，例如样例中：

- `AVERTISSEMENT`
- `LEÇON DU 10 JANVIER 1979`

原因很简单：

- 数字脚注和数字尾注会重号
- 同一本书里不同 section 的注释体系可能完全不同
- 尾注通常只对当前章/讲/节生效

也就是说，`1` 不是全书唯一键，真正的唯一键应该是：

- `section_id + note_kind + normalized_marker`

### 第二步：识别正文引用标记

正文里的引用标记至少要统一成一种内部形式。样例里已经出现了这些输入形态：

- Unicode 上标数字：`¹²³`
- OCR 数学化上标：`$ ^{5} $`
- 星号类标记：`*`、`**`

推荐先标准化成内部 marker：

- `¹` -> `1`
- `²` -> `2`
- `$ ^{13} $` -> `13`
- `*` -> `*`
- `**` -> `**`

这一步只做“识别与归一化”，不做脚注/尾注归类。

### 第三步：识别显式尾注区

如果某个 block 或 markdown 行匹配以下标题，应立即切换到尾注区状态：

- `NOTES`
- `ENDNOTES`
- `尾注`
- `注释`

一旦进入尾注区：

- 后续连续的 `text` 或 `footnote` block，如果以 `数字 + 点/右括号` 开头，应优先视为尾注定义。
- 没有新编号但紧跟其后的 block，视为上一条尾注的续块。

样例里第 31 页 `### NOTES` 之后，第 31-34 页都应该归到尾注区。

### 第四步：识别页脚脚注区

在还没进入尾注区之前，`block_label == footnote` 的 block 默认视为脚注候选。

但这里不能直接“一块等于一条脚注”。需要再做一次匹配：

1. 如果 block 以 marker 开头，而且这个 marker 能在同页正文引用里找到，就把它视为一个新脚注的起点。
2. 如果 block 不以 marker 开头，或者虽然以数字开头但这个数字不在同页正文引用集合里，就把它并到上一条脚注。

这条规则就是为了吃掉第 29-30 页那种情况：

- 正文真实引用是 `*`
- 后面的 `1. 2. 3. 4.` 只是脚注内部列表，不是新尾注

### 第五步：识别跨页脚注延续

脚注不能在页末强行截断。

推荐规则：

1. 某页末尾已经打开了一条脚注。
2. 下一页在 `NOTES` 标题出现前，最先出现的仍然是脚注块。
3. 且该脚注块不是一个“能和下一页正文引用匹配上的新 marker”。

满足这三条，就把下一页开头脚注块并入上一条脚注，视为跨页延续。

样例中：

- 第 29 页的星号脚注应延续到第 30 页。
- 第 1 页的第 `4` 条脚注不应延续到第 2 页，因为第 2 页出现的是新的 `5.` 和 `6.`。

## 输出数据模型

建议筛选器输出一份中间 manifest，而不是直接拼最终 markdown。最少应有这几层：

```json
{
  "sections": [
    {
      "section_id": "sec-02-lecon-du-10-janvier-1979",
      "body_segments": [],
      "footnotes": [
        {
          "id": "fn-02-0008",
          "original_marker": "*",
          "pages": [29, 30],
          "text": "..."
        }
      ],
      "endnotes": [
        {
          "id": "en-02-0001",
          "original_marker": "1",
          "pages": [31],
          "text": "..."
        }
      ]
    }
  ]
}
```

这里的关键不是 JSON 长什么样，而是：

- `footnote` 和 `endnote` 分表
- 每条注有稳定 ID
- 保留 `original_marker`
- 保留 `pages`
- 文本续块已经提前合并

## Obsidian 编码方案

Obsidian 原生只认脚注，不认尾注。所以两类注释必须故意用两套表示法。

### 脚注：继续使用 Obsidian 原生脚注

正文中：

```markdown
... texte[^fn-02-0003]
```

定义区：

```markdown
[^fn-02-0003]: 这里是脚注正文
```

优点：

- 阅读视图里会自动渲染成脚注
- 命名脚注 ID 可以稳定，不依赖最终显示数字
- 同一个脚注可重复引用

### 尾注：不要再用 `[^...]`

否则 Obsidian 会把它也当脚注，脚注/尾注就合并了。

更稳妥的做法是：

正文里使用显式尾注 token：

```markdown
... texte[EN-02-0007]
```

文末保留独立尾注区：

```markdown
## Endnotes

[EN-02-0007] 这里是尾注正文
```

这样做的好处：

- 在源码层面，脚注和尾注永远不会混淆
- 阅读视图中，脚注会自动沉到底部，尾注则作为独立章节保留
- 后续如果你想把 `[EN-02-0007]` 升级成内部链接、块链接或插件语法，也有清晰的升级点

## 翻译阶段的保形策略

这里最重要的一点是：不要直接把“最终显示形式”扔给大模型翻译。

推荐做法是先转成冻结 token，再翻译，再回填：

### 1. 正文中的引用先替换成冻结 token

例如：

- `[^fn-02-0003]` -> `{{FN_REF:fn-02-0003}}`
- `[EN-02-0007]` -> `{{EN_REF:en-02-0007}}`

### 2. 注释定义也分开翻译

不要把正文和所有注释混成一个长上下文一次翻完。更稳的是：

- 正文分段翻译
- `footnotes[]` 单独翻译
- `endnotes[]` 单独翻译

这样可以避免：

- 大模型重编号
- 大模型把尾注改成脚注
- 大模型把 `*`、`**`、数字 marker 擅自统一

### 3. 翻译完成后再做回填

最终回填规则：

- `{{FN_REF:...}}` -> `[^fn-... ]`
- `{{EN_REF:...}}` -> `[EN-...]`
- 再把翻译后的脚注定义和尾注定义按各自区域写回

这一步应由后处理脚本完成，不交给大模型。

## 样例上应达到的结果

按当前样例，理想输出应该至少满足：

- `AVERTISSEMENT` section
  - 识别出页脚脚注 `1-8`
  - 不应出现尾注
- `LEÇON DU 10 JANVIER 1979` section
  - 识别出多个星号脚注
  - 第 29-30 页的星号脚注合并为一条
  - `### NOTES` 后的 `1-18` 识别为尾注

## 当前仓库里的原型

已经加入一个可直接跑样例 JSON 的原型脚本：

- [`scripts/footnote_endnote_filter_prototype.py`](../scripts/footnote_endnote_filter_prototype.py)

它当前做的是：

- 按 `doc_title` 切 section
- 从 markdown 中提取正文引用 marker
- 从 JSON 中提取脚注块
- 识别 `NOTES` 尾注区
- 合并跨页脚注
- 输出脚注/尾注清单摘要或完整 JSON manifest

这还不是最终生产版，但已经可以用来验证核心状态机是否合理。
